# AET-WO-4412 results, part (1): what happens today

**STOP: §7, "after (1), with the table and the triage."** Measured 2026-11-26 on Furnace, against main `eea3198e`. Today's rows use the unpatched CLI; any other run says what it is. No crate is changed on this branch. The one CI change is `TIER2_MIN` 205 → 209 (`1919` F11).

## The answer first

1. **Neither out-of-memory death reproduces.** Both `4400h` deaths were measured before `4400j` found the console queue (about 48 MiB per wall second). Inferred: both were that queue, fed by long wall times.
   - **DShot over MAVLink today is a hang, not a memory death.** The CLI kills it at the 120 s guard as a `ToolError`, so no verdict is written (2 of 2). Peak RSS stays flat at about 0.5 GB.
   - **Diagnosed by replay: Renode's timer at DShot600's bit rate.** At ARR 7 TIM1 updates about 595,000 times per virtual second. Each update fires `STM32_Timer`'s limit handler and re-arms four channel timers (`STM32_Timer.cs`:50–137). That costs about 25 s of wall per virtual second; the armed run costs about 3.5 s.
   - Holding ARR at PWM's 0x9C3 alone brings the run back to 42 s. Disabling the DMA stream alone leaves it at 167 s. The logging is not the cost: silenced, it still took 164 s.
2. **No DShot bit leaves the twin, and the DMA request is not what moves the data.**
   - ArduPilot sets `UDE` and maps DMAMUX1 channel 9 to request 15 (TIM1_UP) 4,143 times.
   - Renode's `STM32DMA` moves a memory-to-peripheral stream whole at `EN`, with no request (`STM32DMA.cs`:237–245).
   - All 530,936 words land in TIM1 `DMAR` (0x4C), which the stock timer does not model ("Unhandled write"). So no CCR moves.
3. **A foreign firmware reboots in the twin with one macro, and the second boot fits.**
   - Today, with no macro, Renode resets the peripherals and starts the core at PC 0. ArduPilot faults, and the verdict is `fail` (`pc_outside_firmware`, `core_in_exception`, `foreign_clock_contradicted`): **a commanded reboot is judged as a crash.**
   - With a `reset` macro of the CLI's own boot lines (patched, replay), the second boot runs. Parameters set over MAVLink before the reboot read back after it (`FRAME_CLASS` 1 and `COMPASS_USE` 0, 0.81 s after the reset). The second boot reaches `ArduPilot Ready` at 11.642 s.
   - The managed heap grows by 266,892 B across the reboot, almost all of it Renode's symbol table re-read by `LoadELF`. RSS stays flat at about 0.5 GB.
   - Flash, the backup registers and DTCM survive Renode's reset. `RCC_RSR` reads the power-on flags, not `SFTRSTF`.
4. **The board.**
   - Main's Sentinel-03 is refused `ForeignClockUndeclared` before Renode.
   - With `foreign_clock` derived, it arms and passes, but **`judge_foreign` judges none of its 16 clocks** ("the tree is PLL1 (PLLSRC 10), whose deviation is not declared").
   - A spec carrying `foreign_clock` is refused on every generated run (`ForeignClockOnGeneratedRun`). So committing it in `examples/sentinel-03.json` as it stands breaks `verify` and the bench package. That is decision D1.
5. **DMA per timer:** RM0433 Rev 9 Table 124 (p. 697) gives **TIM12, TIM13 and TIM14 no request.** The solver offers them for DShot (`motor.rs`:733). No committed DShot board uses them.
6. **Triage:** none of R2–R8 needs slice B. The RC baud row is closed: 416666 is inside the declared tolerance, and the hwdef already names it.

## 4. Decisions for the architect

- **D1. Where Sentinel-03's `foreign_clock` lives** (2). Committed as it stands, every generated run refuses it (`ForeignClockOnGeneratedRun`, measured), so `verify` and `bench-package-s03` break.
  - **(a), lean:** generated runs ignore `mcu.foreign_clock`, so the refusal is lifted for them, and `validate` refuses a `foreign_clock` that disagrees with ArduPilot's tree for the declared crystal. That tree is the pinned image's `stm32h7_mcuconf.h`, held as cited data: 16 MHz gives USARTs 100 MHz and timers 200 MHz. This is "derived from the specification's crystal". It moves Sentinel-03's spec hash, so its package re-derives by dispatch.
  - (b) A second committed spec for the ArduPilot build. That is two sources for one board (`INV-01`).
  - (c) The engine derives the clock at run time from `mcu.hse` and the held table, with no spec field. The WO's "commits its derived clock" rules this out.
- **D2. `judge_foreign` on PLLSRC = HSE** (2). Lean: judge each clock at the HSE's fastest, the crystal's declared fast ppm (`clock.hse`, `4240a`'s budget), as the generated judge does. It moves only foreign verdicts on HSE boards (today Sentinel-03's: 16 `not_judged` become judged).
- **D3. `MOT_PWM_TYPE` and the ordering hazard** (2). It is a parameter, so it goes in a `defaults.parm` that `generate hwdef` writes beside `hwdef.dat`. Whether the pinned build embeds that file is to be confirmed in the build. **If it lands before (3), every Sentinel-03 foreign run engages DShot from boot and hangs at the 120 s guard** (this table). Lean: build the `MOT_PWM_TYPE` bullet as the last step of (3), not in (2).
- **D4. The motors** (3). The measured cause is Renode's per-update timer cost, and the DMA moving data at `EN` into an unmodelled `DMAR`.
  - **(a), lean:** a timer model of our own for the DShot-capable timers. It counts lazily, so an update fires no event unless an interrupt, a DMA request or an observed edge needs it. `UDE` raises the UP request on DMAMUX1 by Table 124, and the model takes the `DCR`/`DMAR` burst into `CCR1–4`. Beside it, a DMA overlay that paces a memory-to-peripheral stream by its request, so the stream ends as silicon's does (`NDTR` words, `TCIF`).
    - The foreign judge then decodes each DShot frame from the `CCR` burst (throttle, telemetry bit, CRC). It reads TIM1 at the window's end with no stop, so the end-of-window stop is "removed" on the foreign path.
    - It moves every emitted platform that names a timer, so INV-08's committed boards' `.repl` goldens move (each named) but not their verdicts, if the generated path keeps its stop.
  - (b) Refuse by name when a foreign firmware sets `UDE` (`timer_dma_unmodelled`, the timer, the request, the instant), and halt. This is bounded and cheap. But the acceptance's "arms with DShot engaged over MAVLink and judged" then cannot be met, because DShot engages at 6.18 s and the arm comes at 8.75 s.
  - **Solver (both):** DShot only on a timer with an UP request on Table 124 (`NoDshotDmaRequest` on TIM12–14). No committed board moves.
- **D5. The reboot** (4) is feasible as measured: second boot inside the cap (about 0.5 GB), parameters judged after it.
  - **Lean:** a `reset` macro of the boot lines without `LoadELF`. Flash survives Renode's reset, so reloading is not the bench's reset and would hide a firmware that wrote into its own image. `cpu VectorTableOffset` is the line that matters.
  - Set `RCC_RSR` to a software reset's flags, per RM0433 §8.4.4's table, so ArduPilot reads the reset cause silicon gives.
  - A reboot input must reboot by about 6.7 s to see the second boot's Ready inside 12 s (11.642 s). Arming after a reboot does not fit the window.
- **D6. The `4400h` rows' text:** "runs out of memory" in §7.1 (the DShot row and the reboot row) is not today's behaviour. Lean: the docs PR rewrites them from this table.
