## 3. The archive header (`2205` F4)

**Corrected after the adversarial pass.** This section first said the header was in no hash, from the README's description of the chain; that was wrong, and the replayer was not read.

**Not committed anywhere that is compared** [read].
- Archives (`trace.cbor`) are committed only under `spike/`, as records.
- `aethelgard-chaos/tests/golden.rs` pins a golden trace whose header the test builds itself, with no engine version.

**But hashed into a committed byte** [read, and demonstrated by the adversarial pass].
- `Replayer::new` seeds the state-sequence hash with the sha256 of the header's bytes (`chaos/src/replay.rs:96`, from the writer at `archive.rs:144`), and the header's `tools` hold the engine's entry.
- That hash is each run's `state_sequence_hash`, in `verify`'s `campaign` runs (`verify.rs:461`), so it reaches the verdict and `MANIFEST.json`'s `verdict_sha256`.
- Two headers that differ only in the engine string give different seeds: `…, clean` against `…, dirty`, and one commit against another.
- What does not depend on it: `run_id`, a function of the scenario's, the specification's and the firmware's hashes (`chaos/src/campaign.rs:1689`); and `verify`'s reading of the header, which is only for the Renode build (`verify.rs:2828`).

**So the header cannot carry the commit:** that is §7's second stop, reported. It names the version alone, as before this work order. A version change already moves `verdict_sha256` through `engine_version`, so the bump moves no further committed byte through the header (no test pins a real run's state hash; `git grep`).

## 7. Found while measuring: three things outside the fence

1. **CI's bench write refuses at a new version.**
   - The bench-package dispatch runs `verify --fab-out … --rebind fab/sentinel-01-bench/package` (`ci.yml:600`, `AET-WO-4300k`).
   - `rebind` lets only the binding move: in `MANIFEST.json`, the specification, topology, verdict, scenario and FAB-NOTES hashes; in `FAB-NOTES.md`, the specification line.
   - It refuses `FAB-NOTES.md`'s `Generated by aethelgard <v>` line. Its own test holds `0.2.0 → 0.2.1` refused (`rebind.rs:244`).
   - So §1 step 4's write dispatch cannot regenerate Sentinel-01's package at 0.3.0, nor at the `0.4.0-dev` of (4) [measured, above].
   - **Ruled (a), 2026-11-26T20:19Z:** `rebind` admits that line too, moving only to the deriving engine's own `CARGO_PKG_VERSION`. The fence widens to `rebind.rs` and its tests.
2. **CI's packaging step refuses a `-dev` version.**
   - `ci.yml:135` requires `^[0-9]+\.[0-9]+\.[0-9]+$` [measured: `0.4.0-dev` does not match].
   - So (4)'s PR is red until `ci.yml` admits a pre-release.
   - **Ruled 20:19Z:** in (4)'s PR, exactly `^[0-9]+\.[0-9]+\.[0-9]+(-dev)?$`; the release documents say a `-dev` version is never published.
3. **The engine image cannot know its commit.**
   - Its build context excludes `.git/` (`.dockerignore`), and the build binds the context, not a package (`container/engine.Dockerfile`).
   - So by the work order's two sources, the image's `aethelgard --version` says `commit unknown`. That is true, but it is the supported interface (README).
   - **Ruled 20:19Z: a backlog row** (build the image from a `cargo package`d CLI). The image's commit is its `org.opencontainers.image.revision` label (`engine-image.yml:69, 154`, checked at `:160`), and the release notes say so.
