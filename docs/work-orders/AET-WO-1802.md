# AET-WO-1802 — The engine names itself truthfully, then the 0.3.0 release

**Repo:** `ClearForge-LLC/aethelgard` · **Base:** `main`, named in the kickoff.
**Branch:** `wo/aet-1802-identity-0.3.0`.
**Author:** Claude (architect) · **Builder:** strong tier (the `4411` builder), with a targeted adversarial pass on the identity and the packaging.
**Phase:** release. Written 2026-11-26 at Scotty's ask ("the header fix and bump to 0.3.0 sooner rather than later"; 0.4.0 at P4's exit). **Cadence:** measure and build now. The bump and the package regeneration land once, in a quiet window after `AET-WO-4412` (#410) merges (§1 step 4).

**Grounds:**
- **A false name on a fabrication package.** `fab/sentinel-03/package/FAB-NOTES.md` line 3 says "Generated by aethelgard 0.2.0". 0.2.0 reads specification 13, and that board is specification 31. Every package built from `main` since 2026-11-17 makes the same claim: 221 commits, and schema 13 → 31.
- **§7.1, `2205` F4:** "The engine's version in the archive header is the package version, not a commit."
- **0.2.0 is stale on crates.io.** It reads specification 13 and can read no committed example. `aethelgard-hwdef` has never been published (`docs/releasing.md` order item 10).
- **`RUL-21`:** a release is a pinned snapshot with no update promise. **`AET-WO-1801`:** the procedure, `docs/releasing.md`, `RELEASE-0.2.0.md`'s form.
- **`INV-08`:** byte-identical outputs for one input. **The constraint that shapes this work order:** a committed package is checked by `--against-fab` on every PR, and its MANIFEST binds `verdict_sha256`.
  - So **a commit hash written into any committed or hashed byte would make every package stale on every commit.**
  - The commit can only go where no committed byte moves. The version has to be made true in another way.

> **What this is:**
> - **(1) The engine's identity, made true where it is written:**
>   - **The version** stays in the bytes it is in today (FAB-NOTES, the KiCad generator fields, the hwdef header, the verdict's `engine_version`). It is made true by never naming a release `main` is not.
>   - Between releases, `main` carries the next version with a pre-release suffix (`0.4.0-dev`), so a package built from `main` says "aethelgard 0.4.0-dev", never a published version it is not.
>   - The version moves only at a release and in the commit right after it, so committed bytes still move only then.
> - **(2) The commit, where no committed byte moves:**
>   - `aethelgard --version`, `doctor`, the MCP server's info, and the trace/archive header (`2205` F4) if the archive is not a committed golden.
>   - Recorded from the build: git at build time, or the packaged crate's `.cargo_vcs_info.json` for a crates.io build.
>   - A build with no known commit says `commit: unknown`, never a default. A build from a dirty tree says `dirty`.
> - **(3) The 0.3.0 release, as `1801` did 0.2.0:**
>   - every crate at 0.3.0, packaging proven;
>   - `aethelgard-hwdef`'s first publish prepared, plus any other crate crates.io has never seen;
>   - `docs/releasing.md` updated;
>   - `RELEASE-0.3.0.md` for Scotty, with the exact commands, the token scopes (`publish-new` for the new crates), what each command prints, and the check after;
>   - release notes: what 0.3.0 does that 0.2.0 did not, each item cited to its work order. Specification 31 is read; 0.2.0 read 13.
> - **(4) After Scotty publishes:** a follow-up PR from this branch sets `main` to `0.4.0-dev` and regenerates.
>
> It is NOT:
> - the publish (Scotty's, from his workstation);
> - the README's install line (an architect docs PR, after the publish);
> - any behaviour change other than the identity.

## 5. Adversarial pass, targeted

- **An identity that lies:**
  - a commit named for a dirty tree;
  - a crates.io build claiming a commit it was not packaged from;
  - a `-dev` build that prints a release's version anywhere.
- **A commit that leaks into a committed byte** (through the verdict, a header or a fixture), so the next commit makes a package stale.
- **A crate that builds in the workspace but not from its package,** or a dependency published after its dependant.

## 7. Flag-and-stop conditions

- **The bump moves a byte `ORDERED.sha256` binds.**
- **An identity site cannot carry the commit without moving a committed byte,** yet `2205` F4 needs it there.
- **A crate cannot be published, or is over 10 MB.**
- **The bump moves a byte that is not the version or derived from it.**
