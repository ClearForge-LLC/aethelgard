  - `crates/aethelgard-cli/tests/`.

> **What this is:** `aethelgard mcp` speaks the Model Context Protocol on stdin and stdout.
> - Its tool list is computed at startup from the `clap` command tree, one tool per leaf subcommand.
> - Each tool call runs the binary itself, as a child, with an argument vector built only from that subcommand's declared arguments. So every call gets exactly the CLI's sandbox, exit codes and JSON verdict.
>
> It is NOT:
> - an HTTP transport or any listener;
> - authentication;
> - adding the binary to the tools image, which is `AET-WO-1501`;
> - new tool behaviour.
>
> **Why now:** this is the surface agents use, and both its sandbox preconditions, `AET-WO-0300a` and `AET-WO-0300b`, have merged.

**Cadence:** build-only. Stop only on §7, which includes the case where `rmcp` cannot serve a hand-built tool list. One PR, left unmerged.

## 1. Scope

1. **The subcommand.**
   - `aethelgard mcp` takes no arguments.
   - It serves MCP over stdio with **`rmcp` 3.7.0** (2026-10-22, Apache-2.0, MSRV 1.88), declared as `default-features = false, features = ["server", "transport-io"]`, and never an HTTP or auth feature.
   - It uses **`tokio`** with `rt`, `macros`, `io-std`, `process` and `signal`, on a current-thread runtime built with `enable_all()`.
   - **The `rmcp` 3.x API, as verified by the architect's reviewer.** Tutorials written for 0.x do not compile against it:
     - implement `ServerHandler::list_tools` and `call_tool`; there are no `#[tool]` macros;
     - build each tool with `Tool::new(name, description, Arc<JsonObject>)`, because `Tool` is `#[non_exhaustive]`;
     - `call_tool` returns `CallToolResponse`;
     - `get_info` must enable tools;
     - `rmcp` does not validate tool arguments, so this module must;
     - `rmcp` caps an incoming line at 16 MiB. It drops an oversized line without replying, so the client waits.
   - It exits 0 when stdin closes.
   - It writes nothing to stdout except protocol messages. Diagnostics go to stderr.
   - **At startup, before the runtime starts,** it runs the same inherited-descriptor check the trampoline runs (`run.rs`, `inherited_descriptors`). A descriptor above 2 without close-on-exec refuses with exit 4, `SandboxUnavailable`, `id` `descriptors`. Otherwise every tool call would be refused later, one at a time, for the same reason.
2. **The tool list.**
   - **Generated by one function, `tools(&clap::Command) -> Vec<Tool>`,** in `src/mcp.rs`. It is applied to the **unbuilt** `Cli::command()`, never to a built one: a built command grows `help` subcommands at every level and a `help` argument on every subcommand.
     - Every leaf subcommand becomes one tool, named by its path joined with `_`: `validate`, `check_drc`, `check_erc`, `prove`, `simulate`.
     - `help` is excluded at every level, and so is `mcp` itself.
     - Arguments whose action is `Help` or `Version` are dropped.
   - **Each tool's description** is the subcommand's `about` text.
   - **Each tool's input schema** is a JSON object with one string property per declared argument, keyed by the argument's **long name** from `get_long()`. Note that `prove`'s field is `crate_dir` but its long name is `crate`. A property is `required` exactly when `clap` requires it, and `additionalProperties` is false.
   - **`tools()` panics, under a unit test, on any argument it cannot map:** one with no long name, such as a positional, or one whose action is not `Set`, such as a boolean flag. Today's tree has neither. The panic makes a future one a build-time failure, never a silently wrong schema.
   - **Nothing about a tool is written by hand** in the `mcp` module. A change to the command tree changes the list.
3. **A tool call.**
   1. Find the tool by name. An unknown name is an MCP error.
   2. Check the arguments against the generated schema: only declared names, every value a string, required ones present. Any other shape is an MCP invalid-params error, and no child is spawned.
   3. Build the child's argument vector from the subcommand path, plus one `--<long>=<value>` token per argument. Using one token per argument means a value that starts with `-` cannot be read as a flag. A value containing NUL is refused.
      - The vector's first element is always a subcommand name from the tree, never one of the internal first arguments.
      - Add a test that `tools()` can never produce a tool named like an internal argument, or like `mcp`.
   4. Spawn `std::env::current_exe()` with that vector, with stdin as `/dev/null`, stdout captured and capped at 1 MiB (over the cap is a tool error), and stderr captured for the diagnostic only.
   5. **The result:**
      - the text content is the child's stdout line, unchanged;
      - the structured content is `{"exit_code": <n or null>, "verdict": <the child's JSON object>}`, so the child's object is never edited;
      - `isError` is false for exit 0 or 1, because a fail verdict is a successful call. It is true for every other exit, for a child killed by a signal (`exit_code` null), and for stdout that is not exactly one JSON line.
   6. **Output bounds.** stdout is capped at 1 MiB and stderr at 64 KiB. Past either cap, the module kills the child, keeps draining both pipes until they close, and returns `isError` true naming the cap. Never stop reading while the child lives, or the call hangs: `RUL-13` sets no timeout.
4. **Cancellation and shutdown.** `rmcp` never aborts a handler. It only cancels the request's token, and when stdin closes it waits up to 5 s for running handlers before it cancels them.
   - Each call therefore uses `select!` on the child's exit and on `context.ct.cancelled()`, and kills the child on cancel.
   - `mcp` also handles SIGTERM and SIGINT by killing every live child, and then exits.
   - Killing the CLI child is enough to end a call. Its reaper watches it and ends the tool's whole process group (`architecture.md` §6). Nothing watches the `mcp` process itself, so this module must do the killing.
5. **`validate` through MCP.** The child's stdin is `/dev/null`, so a `validate` call without `file` is refused as empty input, and the result says so. That is the CLI's behaviour, unchanged. README says to pass `file`. An inline specification argument is not in this work order.
5a. **`path` in the refusal envelope** (`AET-WO-1100` FEEDBACK A7, ruled at review of PR #25). The CLI's refusal envelope gains an optional `path` field. It carries the JSON path for `InvalidIdentifier`, and is absent otherwise. An agent then reads the path as a field, not from the human-readable message. This is the one change to the CLI's output contract this work order makes. The README's exit-2 row says so, and `validate_cli.rs` gains one test.
6. **`crates/aethelgard-cli/README.md`.** The root `README.md` is protected. Add a `mcp` section covering:
   - how to run it;
   - the generated tool list;
   - the result shape;
   - `isError`;
   - cancellation;
   - how to point MCP Inspector at it (`npx @modelcontextprotocol/inspector aethelgard mcp`), as the human check of the gate clause.

## 3. Tests and acceptance, proven not asserted

1. **A stdio protocol test** (tier 1, in `gates`). It spawns `aethelgard mcp` and speaks JSON-RPC to it: `initialize`, then `tools/list`, which must equal the five tools, and then `tools/call` twice.
   - **The paths.** Example paths are absolute, built from `CARGO_MANIFEST_DIR/../../examples/`. A test's working directory is the crate's own, and the crate has its own `examples/`.
   - **The valid call.** `validate` on `sentinel-01-minimal.json` returns exit 0, with `isError` false.
   - **The zeroed call.** `validate` on `invalid-zero-domain.json` returns exit 2, with `isError` true, naming the domain.
2. **The throwaway-subcommand clause, as a unit test of `tools()` in `src/mcp.rs`.** The crate is binary-only, so integration tests cannot call `tools()`, and adding a `src/lib.rs` would change what `workspace_shape.rs` checks. So the test is in the module itself: `tools()`, applied to a `clap::Command` built in the test with one extra leaf subcommand, lists that subcommand. Further unit tests of the same function:
   - its panic on a positional argument and on a boolean flag;
   - that no tool can be named like an internal first argument, or like `mcp` or `help`.
3. **Argument checking, as unit tests of the pure `argv()` builder.** It returns either a vector or a refusal. Each of these refuses:
   - an unknown argument;
   - a non-string value;
   - a missing required argument;
   - a value containing NUL;
   - an unknown tool name.

   Separately, a value starting with `--` is **not** refused. It becomes the single token `--<long>=--…`, and the CLI judges it. Test that the token is built exactly so.
4. **Tier 2, in `tools`:** `check_drc` on the clean and violation fixtures, which must give `isError` false both times, and exit 0 and 1. `prove` on the seeded overflow, and `simulate` on the Nucleo board.
5. **Cancellation and shutdown.** Use a blocking stand-in tool, following `tools_tier1.rs`'s stub toolbox, in tier 1. Record the PIDs of every descendant of the `mcp` process from `/proc`, then poll until a deadline for all of them to be gone. The child CLI, its reaper, its guardian and the tool are each in their own process group, so a group check proves nothing. Three cases:
   - a `notifications/cancelled`;
   - stdin closed, then SIGTERM, during a call;
   - SIGTERM alone.
6. **The no-listener test.** It searches `src/` only, for the exact tokens `TcpListener`, `UnixListener`, `UdpSocket` and `.bind(`. Comments in `run.rs` already use the word "bind", so a bare-word grep would fail. It also checks that the crate's `rmcp` features are exactly `server` and `transport-io`.
7. The workspace gates pass, and CI is green on the first push.

## 4. Scope fence

- HTTP, SSE or any streamable transport.
- Authentication.
- Resources or prompts, which are MCP features beyond tools.

- Changing any existing subcommand's behaviour.

## 5. Adversarial pass — full, by a strong reviewer

Hand it to a fresh subagent on a strong model. Every finding goes in FEEDBACK with a severity.

1. **Reach an internal first argument, or any argument vector not built from the tree.** Try:
   - tool names with `_`, `.` or `/`;
   - argument names that collide with `clap` built-ins (`help`, `version`);
   - Unicode look-alikes;
   - values carrying `=`, newlines, or `--`.
2. **Make a fail look like a pass, or a tool error look like a verdict,** through the result mapping.
3. **Exhaust the server:**
   - very large JSON-RPC messages;
   - many concurrent calls;
   - a child that prints forever;
   - a client that never reads.

   Say what `rmcp` bounds and what this module bounds.
4. **Leave something running after the client disconnects mid-call.**
