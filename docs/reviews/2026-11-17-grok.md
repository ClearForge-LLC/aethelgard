## Round 1

**Yes. Pulled and reviewed.**

`aethelgard` 0.2.0 (workspace) is on crates.io. The repo is at `https://github.com/ClearForge-LLC/aethelgard`. I cloned it into the sandbox, confirmed the published crates, and `cargo install aethelgard-cli --version 0.2.0 --locked` succeeded. The resulting `aethelgard` binary runs.

This is a carefully engineered multi-crate workspace whose north star is co-generation and co-verification of a board + firmware from one specification, before fabrication. The areas you flagged are the right ones for an outside eye.

### 1. New-user path (crates.io → validated board)

**What works**

- `cargo install aethelgard-cli` gives a working binary.
- Pure-Rust commands (`validate`, `solve`) need no external tools. Against the reference `examples/sentinel-01-minimal.json` (schema_version 13) it returns `{"ok":true,...}` and exit 0.
- A minimal malformed document is refused with a structured JSON error (`SchemaViolation`, missing field) and non-zero exit. The contract is documented in `crates/aethelgard-cli/README.md` (exit codes, `RUL-10`).
- The published image quickstart in the root README is deterministic: it pins the image by digest, checks the spec hash, and exercises emit → ERC → DRC → a deliberate `PinClaimedTwice` refusal.

**Friction for a stranger**

- The root README still says the crates.io release is 0.1.0 and “0.2.0 will replace it.” That is now stale. A new reader following the text will be pointed at the Docker image as the supported interface, which is accurate for the full flow (KiCad, Renode, ngspice, Kani, etc.), but it understates what a pure `cargo install` already gives.
- Full “validated board” (emit + ERC/DRC + later gates) is not available from the crates.io binary alone. The tools live in the image; the CLI refuses to run them without the sandbox conditions being met. This is intentional and documented, but the path from “I just installed the crate” to “I have a board that passed ERC/DRC” is the image, not the binary.
- Schema is at version 13. Older files are refused. That is correct, but the README does not yet surface the current schema version or a minimal “cargo install then validate” snippet next to the Docker quickstart.

**Verdict:** A stranger can get a working binary and validate a modern specification today. Getting to a checked board still routes through the image. The documentation lag on the 0.2.0 status is the main paper cut.

### 2. CLI subprocess and sandbox surface

This is the strongest part of the design.

`crates/aethelgard-cli/src/run.rs` implements a three-process arrangement:

- The CLI never execs a tool directly.
- It starts a *reaper* (new process group, empty environment, private scratch).
- The reaper starts a *trampoline* that:
  - Applies Landlock (ABI-dependent: filesystem, TCP bind/connect on ABI ≥4, signal/abstract-socket scoping on ABI ≥6).
  - Installs a hand-assembled seccomp-BPF filter that refuses every `socket()` family (including the x32 hole that `seccompiler` cannot express cleanly) and `io_uring`.
  - Drops capabilities, sets rlimits (`RLIMIT_FSIZE` 64 MiB, etc.), and switches to a fixed uid/gid when running as root.
- Scratch lives under a checked base (`TMPDIR` or `$HOME/.cache/aethelgard` / `/var/lib/aethelgard`). Ownership, mode, and path-character constraints are enforced before any tool runs. `/tmp` is refused. A violation is `ScratchUnsafe` / exit 4.
- The status file the CLI reads lives outside the tool’s writable tree, so the tool cannot forge the sandbox report.
- The verdict always includes a `SandboxReport` (ABI, `tcp_confined`, `scoped`, `sockets_denied` always true, `uid_boundary` and the first unmet condition).

Renode and the ngspice bridge run inside this. The analog path treats the bridge as the owner of its Renode child. If Landlock or seccomp cannot be applied, the call fails closed (`SandboxUnavailable`) rather than running unsandboxed (`INV-06`).

**Observations**

- The design is unusually complete for a hardware-generation tool: reaper, trampoline, capability drop, path-character restrictions to avoid command-language injection, and explicit reporting of what the sandbox actually achieved.
- The x32/seccomp note in the architecture docs is the kind of finding that only appears after adversarial reading of the filter compiler; it is addressed in the implementation.
- Residual surface is the usual one for Landlock+seccomp: UDP is not covered by Landlock, and the effectiveness of the uid boundary depends on the host (rootless podman, toolchain paths, etc.). Those are named in the report rather than hidden.

This is production-grade containment for the tools it launches.

### 3. Malformed input fails closed

Yes, and the mechanisms are layered.

- `Specification` and the major nested types use `#[serde(deny_unknown_fields)]`.
- Schema version is checked; older or missing versions are refused. Current constant is 13.
- Input is size-capped at 16 MiB (`MAX_INPUT_BYTES`); excess is refused unread, never truncated.
- Paths are canonicalized and must be UTF-8 regular files. The bytes are copied into private scratch and hashed before any tool sees them (`INV-03`). The hash in the verdict is of the judged copy.
- Validation refuses rather than defaulting (`INV-06`). Examples in the quickstart and in `aethelgard-ir/tests` cover claim conflicts, missing fields, and type errors.
- CLI exit 2 is reserved for invalid specification; the error object names the kind (`SchemaViolation`, `PinClaimedTwice`, etc.).

I confirmed both the happy path and a missing-field refusal with the installed binary. The fail-closed posture is consistent from the type system through the process boundary.

### 4. Packaging and licensing

Clean and explicit.

- Workspace `version = "0.2.0"`, `license = "MIT OR Apache-2.0"`, edition 2024, `unsafe_code = "forbid"` on workspace crates.
- Every published crate carries its own `LICENSE-MIT` / `LICENSE-APACHE` and a README.
- `aethelgard-kicad-lib` correctly uses the dual license `CC-BY-SA-4.0 AND (MIT OR Apache-2.0)`. KiCad’s vendored symbols/footprints stay CC-BY-SA (with the design exception); the project’s own symbols for parts KiCad lacks are MIT/Apache. The README states the split.
- `aethelgard-renode-models` is a data-only crate holding the C# sensor models; it is under the workspace license.
- Boards and the analog bridge are excluded from the workspace so the `forbid(unsafe)` does not apply to the generated MMIO or the FFI bridge (`RUL-04`, `RUL-17`). That exclusion is documented.
- `RELEASE-0.2.0.md` records the exact publish order and the dry-run procedure. The crates that exist on crates.io match the members.

Nothing obvious is missing from the published crates for the contracts they claim. The dual license on the KiCad data is the one that needs to stay visible; it is.

## Round 2

**Critiques, suggestions, and additions.** Grounded in the 0.2.0 tree, the published crates, the architecture measurements, and the fact that P3 is closing and P4 (flight controller) is starting. First principles where they matter; concrete where the code already decided.

### Schema evolution is the highest practical cost right now

You are at schema version 13 after a sequence of renumberings (the comments in `aethelgard-ir` document the collisions and the “nothing supplies it for an older file” rule). The posture is correct and consistent with `INV-06`: refuse rather than invent defaults. The cost is real.

A specification that was valid last week is now invalid. There is no migration path, no `aethelgard upgrade`, and no documented “what changed and how to add the new required fields.” Downstream (including future you, and any agent that cached an example) will hit this repeatedly while P4 adds SPI timing, power, and sensor capacitance details.

**Suggestion:** Keep the fail-closed rule, but add a thin, explicit migration surface before the schema stabilizes for Sentinel-02.

- A `aethelgard migrate --from N --to 13` (or whatever the next stable is) that either rewrites a file with the new required fields filled from documented defaults *that you have measured*, or refuses with a precise list of what must be supplied by hand.
- Publish the migration table in `aethelgard-ir`’s README (or a `SCHEMA.md`) as a machine-readable list of “version N added X, older files lack it, here is the citation.”
- Pin a “schema epoch” for P4. Once the flight-controller specification shape is known, freeze the version for a release and treat further additions as additive optional fields with explicit `null` meaning “not declared,” rather than renumbering.

The renumbering discipline is good. The missing piece is a way for a human or agent to keep an existing file alive without reverse-engineering the comments.

### New-user path still routes almost entirely through the image

`cargo install aethelgard-cli` works and `validate`/`solve` are usable today. The root README still describes 0.1.0 as current and points the supported path at the image digest. That is accurate for ERC/DRC/Renode/Kani, but it leaves a gap.

**Suggestions:**

- Update the status line. 0.2.0 is live.
- Add a short “binary-only” subsection next to the Docker quickstart: install, validate the reference spec, solve it, and note exactly which subcommands will return `ToolUnusable` or `SandboxUnavailable` without the image.
- In the CLI README, list the external tools and the minimum sandbox conditions required for each family of subcommands. A new reader currently has to infer this from the exit-code table and the architecture measurements.

This is low effort and removes the largest “does this even work from crates.io?” question.

### The silicon disagreement is the most valuable signal you have

The 2026-11-16 bench note in the roadmap (SPI1 raised `MODF` and cleared `MASTER` on the first `SPE`; Renode did not model it) is exactly the scar the northstar says should be recorded. The twin passed what silicon refused.

**Suggestions:**

- Make the feedback loop mechanical. A short “silicon delta” document (or a section in the campaign archive) that records: the register write the firmware issued, the twin’s response, the silicon’s response, and the work order that closed or accepted the gap. The current note is good; a standing place for the next ones will keep them from living only in roadmap prose.
- Decide explicitly whether `check pinout` / the boot judge should grow a “silicon-observed” mode that fails a firmware whose first actions match a known twin-vs-silicon disagreement, or whether those remain documented exceptions until the Renode model is updated. The current posture (send to `4230`, write `SSM`/`SSI` first) is fine for one case; the pattern will recur on a flight controller.
- For P4, treat the twin’s I2C/SPI error models as a known incomplete surface (architecture §2.7 already measured that Renode 1.17.0 has almost none). The first silicon proof of a twin gap arrived on day one of bench work. Budget for more.

### Dual license on `aethelgard-kicad-lib` is correctly declared; the consumption story is thin

The crate is `CC-BY-SA-4.0 AND (MIT OR Apache-2.0)`, with KiCad’s files under the former and your own symbols under the latter. That is the right split, and the README says so.

**Suggestion:** Add one paragraph to the crate README and to the root README that answers the practical question: “If I emit a board from this library, what license obligations do I have?” You already state that boards carry no obligation from the KiCad files. Make the sentence visible at the point of use (the `emit` success message or the generated project’s README) so a downstream fabricator or open-hardware user does not have to hunt for it. The dual license is easy to get wrong later if it stays only in the crate metadata.

### MCP surface is generated from clap; version it

`mcp.rs` builds the tool list from the unbuilt clap tree. That is elegant and avoids drift. The risk is that every new subcommand or argument becomes an MCP tool with no explicit compatibility promise.

**Suggestion:** Document the MCP tool schema as a versioned artifact (even a simple “tools.json” checked into the repo and compared in CI). When you add a required argument or change an exit-code meaning, the MCP contract changes. Callers (including agents) will treat the tool list as stable. A one-line note in the CLI README plus a CI check that the generated tool list matches a committed snapshot would close the gap before P4 adds more commands.

### The unsafe boundary is clean; state the contract for generated boards

Workspace crates forbid `unsafe`. The generated board crate’s `mmio` module is the exception, and there is a test that the generated text contains no `unsafe` outside that module. The exclusion of `boards/` and `bridge/` from the workspace is documented.

**Suggestion:** In `aethelgard-svd-hal`’s README (or the generate command’s output), state the contract in one place: the generated crate is allowed `unsafe` only in the MMIO accessors; everything else is expected to be safe; Kani proofs run over a harness-owned register image, not the real base address (architecture already measured this). Downstream users who vendor a generated board will otherwise wonder whether the `forbid` applies to them. A single sentence prevents the question.

### Campaign and attribution are strong; the dynamic path is still the open risk

Static campaigns are small and fully recorded. Declared droops are also small and not sampled. The architecture notes that per-quantum lock-step reopens the volume question. P4’s flight controller will care about brownout and timing under fault more than the current probe does.

**Suggestion:** Before the first Sentinel-02 specification is frozen, run one dynamic campaign (even a short one) on the current twin and record the actual byte volume and whether the archive still replays cleanly. The northstar and `INV-04` already say sampling is a decision that comes back to you. Having the number before the flight-controller work orders are written is cheaper than discovering it mid-gate.

### Small, high-leverage additions

- **Schema epoch marker.** Once P4’s specification shape is known, tag a version as “P4 baseline” and treat subsequent changes as additive. The current renumbering comments are honest; a named epoch makes the freeze visible.
- **`aethelgard doctor`.** A single subcommand that checks: binary version, whether the sandbox can be installed (Landlock ABI, seccomp), whether the expected tools are on `PATH` or only in the image, and whether scratch ownership is acceptable. It would answer most “why did this fail with exit 4” questions without reading `run.rs`.
- **Example upgrade in the repo.** Keep `examples/sentinel-01-minimal.json` as the current schema, and add a one-commit “what changed” note or a `examples/UPGRADE.md` when you bump the version. Agents and humans both copy the example.
- **First-silicon scar in the northstar.** The SPI `MODF` case is already in the roadmap. A one-line entry under the northstar’s “scars” (or a short `docs/scars.md`) makes the measurement permanent rather than phase-local. You already measured that the twin can pass what silicon refuses; that is the kind of fact the architecture document exists to keep.

### What is already unusually good

The reaper/trampoline + Landlock + hand-written seccomp surface, the copy-and-hash before any tool sees the input, the `deny_unknown_fields` posture, the dual-license declaration, the measurement sections in the architecture document, and the work-order + adversarial-feedback loop are all stronger than most projects at this stage. The first silicon already produced a concrete twin-vs-reality gap and it was recorded. That is the system working as designed.

The highest-value work from here is making the schema evolution and the new-user path as disciplined as the sandbox and the fail-closed input handling already are, and turning the silicon disagreement into a standing feedback mechanism before the flight-controller specifications multiply the surface.
