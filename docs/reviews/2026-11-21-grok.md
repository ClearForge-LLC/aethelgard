Shared by Scotty on 2026-11-21. Grok read the repository at `b1056def` (main at the time of the review) and the published 0.2.0 crates. This document is written for the Claude Opus co-architect and the ClearForge builder fleet: it is citable by work-order number, invariant, and ruling where possible, and it distinguishes measured facts from suggestions. The architect's response (if any) belongs in `2026-11-21-grok.response.md`.

## What is already exceptional

- **Invariants are real and enforced.** `INV-01` (one source), `INV-06` (absence halts; no silent defaults), and especially `INV-07` (gates are not computed from the artifact they judge) appear in types, CLI exit codes, and process. The first-silicon scar (SPI1 `MODF` on the NUCLEO-H753ZI that Renode passed) was written into `northstar.md` the same day and used to close the gap at source (`AET-WO-4230`). That is the system working as designed.
- **Process honesty is load-bearing.** `docs/architecture.md` is a living corrections log. Tool behavior (KiCad exit codes without `--exit-code-violations`, Renode's instruction-level rather than cycle-accurate model, Landlock ABI drift, the seccomp x32 hole, child-process reaping) was measured and the design adjusted. The sandbox (reaper + trampoline + Landlock + hand-written seccomp + capability/rlimit/ownership checks) fails closed (`INV-06`).
- **Separation of concerns is clean.** `Specification` versus `SolvedTopology` (`RUL-16`), workspace `#![forbid(unsafe_code)]`, generated boards and the ngspice bridge excluded so their `unsafe` stays bounded (`RUL-04`, `RUL-17`), copy-and-hash of judged inputs before any tool sees them, structured JSON errors with named kinds.
- **CI and release discipline.** Image pinned by digest, sharded tier-2 tests with inventory guards, publish-order checks, dual license on `aethelgard-kicad-lib` correctly declared.

These properties are uncommon at this stage of a hardware co-generation project.

## Highest-priority critiques

### 1. Schema evolution remains the dominant practical cost (and is accelerating)

The IR is at schema version 22. The fail-closed rule and "nothing supplies a default for an older file" posture are correct and consistent with `INV-06`. The cost is real. A specification that was valid weeks ago is invalid. The version history in `crates/aethelgard-ir/README.md` is excellent documentation; it is not a tool.

The planned complete-list refusal (naming every missing required field with the version and work order that added it) is the right `INV-06`-safe mitigation. It should be treated as near-term rather than backlog. Without an explicit schema epoch once the Sentinel-02 / P4 shape stabilizes, every new flight-controller concern will continue to renumber and invalidate files. This is the failure mode the north star already names: the specification becomes so hard to write that people hand-edit outputs.

**Suggestion (for the next validation work order):** implement the complete-list refusal. When an older file is rejected, emit the full set of required fields the current version demands, each with its version and work-order citation. Keep the refuse-rather-than-default rule intact.

**Suggestion (for P4):** declare a schema epoch once Sentinel-02's shape is known. Further additions become additive optional fields (absent = not declared; explicit `null` refused where that is the existing rule). Publish the epoch number and the policy in one place.

### 2. The twin-to-silicon gap is the project's core scientific risk and is still only partially mechanized

The first scar was valuable precisely because it was recorded and closed at source. Renode's incomplete error models (I2C, SPI `MODF`, clock-synchronization thresholds) are already measured. For a flight controller the surface area grows (timers, DMA, brown-out under dynamic load, sensor models under temperature and supply variation).

**Suggestion:** add a machine-readable silicon-delta ledger. Even a simple CBOR or JSONL side-car in the campaign archive, or a stable schema under `docs/scars/`, that records the triple (firmware action, twin observation, silicon observation) and its disposition. Make the first scar the first entry. This keeps the feedback loop from living only in prose and work-order comments.

### 3. Process overhead is now large enough to be a velocity risk

Work orders, adversarial passes, reduction passes, `FEEDBACK.md` files, amendments, and the rule that the builder never merges are exceptionally strong for auditability. They also impose substantial cognitive and calendar load for a solo or small-team project. The risk is not that the process is wrong; it is that the marginal cost of the next work order grows faster than the marginal reduction in risk.

**Observation for the co-architect:** the north star's own failure modes include "the specification becomes so hard to write…". An analogous failure mode is "the process becomes so heavy that fewer specifications are ever written and judged." The current process is the right default; it should be reviewed for leverage rather than expanded by default.

### 4. Generated artifacts and proof surface are large

`proofs.rs` files in the board crates are already 80–110 kLOC. Kani runs over a harness-owned register image (correctly measured; real peripheral addresses are not owned by the harness). This is the right engineering choice, but the maintenance and review cost of the generated text, plus the time and memory of the proofs, will grow with peripheral complexity.

**Suggestion:** the contract that `unsafe` appears only in the MMIO module is already enforced by test. Stating it in the generated crate's own README (partially done) remains useful for anyone who vendors the output.

### 5. Generality versus depth

The deep, measured focus on STM32H7 (and the honest recording that RP2350/ESP32 lack Renode platforms) is correct for the reference probe. The failure mode named in the north star—"one microcontroller family is supported so deeply that the intermediate representation is secretly that vendor's register map"—is still open.

**Suggestion:** before the IR is frozen for P4, sketch the second-vendor seam. Even a stub pin table and a "this peripheral is not yet modeled" refusal path keeps the IR from calcifying around STM32H7 register names and alternate-function numbers.

### 6. Physical and manufacturing reality beyond the current gates

ERC/DRC, capacitance extraction bounds, rise-time physics from declared pull-ups, power-tree checks, and the analog bridge are substantial. Signal integrity, power integrity under dynamic load, manufacturing tolerances, assembly variation, and EMC are largely future work. That is appropriate for the current phase.

**Observation for P4 exit-gate thinking:** make explicit that "the pair survived simulation" does not yet cover SI/PI/EMC/tolerance. Do not let those concerns be assumed covered.

## Concrete suggestions (prioritized for the co-architect and builders)

1. **Ship the complete-list schema refusal next.** Highest-leverage usability improvement that does not violate `INV-06`.
2. **Declare a P4 schema epoch** once Sentinel-02's shape is known.
3. **Add a machine-readable silicon-delta ledger.**
4. **Implement `aethelgard doctor`.** Binary version, Landlock ABI, whether seccomp can be installed, which tools are present vs image-only, and whether the scratch directory meets ownership/mode rules. Most exit-4 failures become self-explanatory.
5. **Snapshot the MCP tool list in CI.** The current generation from the clap tree is elegant; a committed snapshot plus a diff check prevents silent contract changes for agent callers.
6. **Measure one dynamic campaign's archive volume** before freezing the P4 specification. The architecture already estimates 3–6 MB per simulated second; having the real number removes an open risk from `INV-04`.
7. **Consider a lightweight specification skeleton generator.** Not a migration that invents values, but a command that, given a high-level intent, emits a skeleton at the current schema version with every required field present and commented with its work-order citation. This reduces the blank-page cost without violating fail-closed.

## Out-of-scope observations and companion opportunities

These are explicitly outside Aethelgard's current scope and invariants. They are recorded here so the co-architect and builders can decide whether any of them belong in a future work order, a separate crate, or a separate project.

### Companion systems that would increase the value of Aethelgard without living inside it

- **A specification authoring and migration surface for humans and agents.** A small, separate tool (or a thin layer on top of the CLI) that: (a) emits a fully-commented skeleton at the current schema version from a high-level description, (b) given an older file, produces the complete list of missing fields with citations (the `INV-06`-safe half of migration), and (c) optionally diffs two specifications and names the work orders that explain the difference. This would make the schema evolution cost visible and actionable without putting defaults into Aethelgard itself.
- **A silicon-delta and model-correction database.** A standalone archive (CBOR or JSONL) plus a small viewer that records the triple (firmware action, twin observation, silicon observation) across boards. Aethelgard's campaign archive already has the right shape; this would be the place that accumulates the corrections table so that Renode model improvements or independent rules can be proposed with evidence.
- **An open-hardware parts and footprint library with citation discipline.** `aethelgard-kicad-lib` already does this for a small set of parts, with every value cited to a held document. A broader, community-maintained library that follows the same "no value without a sha256-pinned source" rule would benefit every project that wants to generate boards, not only Aethelgard. The dual-license split already demonstrated is the right pattern.

### A project that does not exist today and should

**A deterministic, citation-backed digital twin for commercial microcontrollers that is not Renode.**

Renode is the best publicly available option and Aethelgard uses it honestly. Its instruction-level model, incomplete error flags, and fixed quanta are measured limitations. A new project whose only goal is "given a vendor SVD + pin table + a small set of peripheral models written against the reference manual, produce a cycle-accurate-enough (or instruction-accurate-with-named-gaps) twin that can be driven from Rust or C and that records every register access with a timestamp" would be useful to every embedded project that currently has to choose between "simulate nothing" and "accept Renode's gaps."

Such a project could start with the STM32H7 (the same part Aethelgard already measured) and treat every unmodeled flag as an explicit refusal rather than a silent pass. It would be a sibling to Aethelgard, not a replacement: Aethelgard would consume its traces the same way it consumes Renode's today. The value is the separation of concerns: one project owns the physics and the peripheral models; the other owns the specification-to-board-and-firmware generation and the gates.

This is not a claim that such a twin is easy. It is a claim that the gap is large enough, and the current best tool honest enough about its limits, that a focused open-source effort would have deep functional value for both human engineers and model-driven toolchains.

## What is already unusually good

The reaper/trampoline + Landlock + hand-written seccomp surface, the copy-and-hash before any tool sees the input, the `deny_unknown_fields` posture, the dual-license declaration, the measurement sections in the architecture document, and the work-order + adversarial-feedback loop are all stronger than most projects at this stage. The first silicon already produced a concrete twin-versus-reality gap and it was recorded. That is the system working as designed.

The highest-value work from here is making the schema evolution and the silicon-delta loop as disciplined as the sandbox and the fail-closed input handling already are, before the flight-controller specifications multiply the surface.
